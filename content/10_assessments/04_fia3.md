# FIA3 - Digital Solution

:::{dropdown} Learning Goals
By the end of this section you will:
- know the conditions and marks for the FIA3 digital solution
- understand how the two-part submission works
- know which documentation tools to use in each phase, and which criteria they provide evidence for
:::

:::{tip} Assessment Details
- Technique: Project – digital solution
- Unit: Unit 2 Application and data solutions
- Mode: multimodal, individual
- Length:
  - visual and written: up to 10 A4 pages, including annotations of up to 1500 words
  - visual and spoken: a video of up to 2 minutes demonstrating the functionality of the data and programmed components
  - the reference list isn't included in the page count
- Marks:
  - Determining and Synthesising: 7
  - Generating: 9
  - Evaluating: 7
  - Communicating: 2
  - Total: 25
:::

In FIA3 we build the data side of a digital solution. The stimulus is a technical proposal for an application that uses the **Model-View-Controller (MVC)** architecture. We are one member of the development team, and we are responsible for the **Model**: the `datastore.py` module that stores and retrieves data from a SQLite database. Other team members are building the View (the user interface) and the Controller.

This means FIA3 focuses on **data and data repositories** and **programmed components**, not on the user interface.

Our code must demonstrate **selection**, **iteration**, **user input** and **data output**.

## The two-part submission

FIA3 is completed in two parts.

1. **Part 1: Design the database.** We determine success criteria and design the database: the data flow diagram, ERD, relational schema and data dictionary. Once we submit our relational schema and data dictionary, we can't change them.
2. **Part 2: Build the datastore.** We receive a repository containing a populated SQLite database and working View and Controller files. We write `datastore.py` so that it meets the requirements of the **Datastore API** described in the repository.

:::{important} Why is it split?
:class: dropdown
Splitting the task means everyone builds their datastore on a workable database. If our Part 1 design has problems, they won't stop us from completing Part 2.

It also means our Part 1 design and the database we are given may differ. That's fine: in the evaluation, we can compare our design with the one we were given, and explain what we would change.
:::

## Structuring your response

Use headings that follow the phases of the problem-solving process.

| Phase | Sections |
| --- | --- |
| Explore | Criteria table |
| Develop | Data flow diagram, ERD and relational schema, data dictionary, pseudocode |
| Generate | Code examples, prototype video |
| Evaluate and Refine | Testing, impacts assessment, product evaluation |
| Bibliography | APA references (excluded from the page count) |
| Appendices | Full code, testing tables |

:::{important} What goes in the appendix
:class: dropdown
Markers can't use anything in the appendix when marking. The appendix is for raw evidence only, such as the full code and the testing tables. The analysis of that evidence must be in the body of the response, where it can earn marks.

See [](../06_documentation/18_appendices.md) for what counts towards the page and word limits.
:::

## Explore

### Criteria table

Use the stimulus to write success criteria for the datastore. The stimulus provides the functional requirements (the data to store and the Datastore API), the non-functional requirements and the user personas. Give each criterion a code (for example, SC1) so we can refer to it throughout the response.

Strong success criteria for FIA3:

- cover the **data** (what is stored, its integrity and reliability) and the **programmed components** (what each method must do)
- consider data privacy and security
- consider both the developer's perspective (the team members who will call our methods) and the users' perspective (the personas)
- are specific, measurable and testable, so we can use them in testing and evaluation

Evidence for: **Determining and Synthesising** (determining success criteria)

See [](../06_documentation/06_success_criteria.md).

## Develop

### Data flow diagram

Show how data moves between the users, the processes in the solution and the data stores. The DFD helps us identify which data each process needs and where it is stored.

Evidence for: **Determining and Synthesising** (data and data repositories)

See [](../06_documentation/10_dfd.md).

### ERD and relational schema

Design the database structure. Identify the entities and the relationships between them, then normalise the data and convert the ERD into a relational schema with primary and foreign keys.

Evidence for: **Determining and Synthesising** (data and data repositories)

See [](../06_documentation/11_erd_rs.md) and [](../04_data/03_structuring_data.md).

### Data dictionary

Describe every field in the database: its name, data type, size, constraints and a description. Include the validation and constraints that protect the integrity of the data.

Evidence for: **Determining and Synthesising** (data and data repositories)

See [](../06_documentation/12_data_dictionaries.md).

:::{caution} Lock in Part 1 carefully
:class: dropdown
We can't change the relational schema or the data dictionary after we submit them. Before submitting, check that:
- every piece of data in the stimulus's functional requirements has a field
- every table has a primary key, and the relationships are shown with foreign keys
- the data is normalised, so no data is stored twice
- data types and constraints suit the data
:::

### Pseudocode

Write pseudocode for the key datastore methods, including the SQL queries they run. Choose methods that do the most important processing, such as those that combine data from several tables or change the data.

Evidence for: **Determining and Synthesising** (programmed components)

See [](../06_documentation/08_pseudocode.md).

:::{hint} Check your work: Determining and Synthesising
:class: dropdown
- Do the success criteria consider the developer's and the users' perspectives, and the data required?
- Are the success criteria authentic, addressing data, security and technical outcomes?
- Do the DFD, ERD, relational schema and data dictionary work together as one consistent design?
- Is the pseudocode structured, unambiguous and specific to the problem?
:::

## Generate

### Code examples

Write `datastore.py` so that every method meets the Datastore API. Then choose the code examples that show the most important programmed components, and annotate each one to explain what it does, why we wrote it that way, and which success criterion it meets. The full code goes in the appendix.

Choose examples that show:

- SQL queries that join tables, filter data or summarise data
- methods that add, update or delete data
- how the methods protect the data, such as using parameterised queries
- selection, iteration, user input and data output

Evidence for: **Generating**

See [](../07_python/05_sql_and_python.md), [](../07_python/06_queries.md), [](../07_python/06_update_delete.md), [](../07_python/08_populate.md), [](../08_sql/01_intro.md) and [](../02_coding/03_good_practice.md).

### Prototype video

Record a video of up to 2 minutes demonstrating the datastore working with the rest of the application. Show how each action in the application calls our methods, and how the data in the database changes as a result.

Evidence for: **Generating**, **Communicating**

:::{hint} Check your work: Generating
:class: dropdown
- Do the data and programmed components work together as one system?
- Does every method behave consistently and reliably, and return what the API says it will?
- Does the solution meet the requirements and the success criteria?
:::

## Evaluate and Refine

### Testing

Test every datastore method (unit testing), then test how the methods work together through the application (integrated testing). Put the testing tables in the appendix, and summarise the key results in the body, referring to specific test cases.

See [](../06_documentation/14_testing.md).

### Product evaluation

Evaluate the datastore against each success criterion. Each judgment must be supported by specific evidence from testing, and must cover the **accuracy and maintainability** of the programmed components. Include refinements we made during development and recommendations for the future, each justified by testing.

See [](../06_documentation/16_evaluation.md).

### Impacts assessment

Evaluate the personal, social and economic impacts of our solution on **data security and privacy**. Consider the personal data the database stores, who can access it, and what would happen if it was lost or exposed. Consider positive and negative impacts from different stakeholders' perspectives, and support each judgment with reasoning.

See [](../06_documentation/17_impacts.md), [](../05_data_transmission/02_privacy.md), [](../05_data_transmission/04_security_management.md) and [](../05_data_transmission/05_security_threats.md).

Evidence for all of the above: **Evaluating**, **Communicating**

:::{hint} Check your work: Evaluating
:class: dropdown
- Are the judgments explicitly connected to the success criteria?
- Is each judgment supported by specific evidence from testing?
- Are the impacts on data security and privacy evaluated, not just described?
- Is there clear evidence of refinements made to the solution?
- Do the recommendations follow logically from the evaluation?
:::

| Communicating | 2 | The whole response |

:::{important} Generating is the biggest criterion
Generating is worth 9 of the 25 marks. A datastore that works reliably with the rest of the application is the most important part of FIA3. Make sure every method meets the API before spending time polishing the documentation.
:::

## Communicating

- Combine diagrams and code with annotations so each one explains and justifies a decision.
- Use technical language accurately for a technical audience (for example, *primary key*, *foreign key*, *normalisation*, *parameterised query*).
- Check the spelling and grammar of every annotation and table.
- Reference all sources using APA style, including in-text citations.
- Stay within the page, word and video limits.

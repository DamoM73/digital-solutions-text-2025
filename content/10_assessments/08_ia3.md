:::{tip} Assessment Details
- Technique: Digital solution
- Unit: Unit 4 Digital impacts
- Mode: multimodal, individual
- Length:
  - visual and written: up to 10 A4 pages, including annotations of up to 1500 words
  - visual and spoken: a video of up to 2 minutes

  - Evaluating: 7
  - Communicating: 2

In IA3 we build a proof-of-concept prototype that exchanges data. The stimulus is a technical proposal that describes the client, their requirements and their users. Our job is to determine success criteria, design and code the solution, then test it, gather user feedback and evaluate it.

IA3 builds on IA2. The big difference is **security**. Unit 4 is about exchanging data, so the data and data repositories must now be **secure**, and the impacts we evaluate are the impacts on **data security and privacy**.

Our code must demonstrate **selection**, **iteration**, **user input** and **data output**.

Use these headings in your response.

:::{important} What goes in the appendix
:class: dropdown
Markers can't use anything in the appendix when marking. The appendix is for raw evidence only: full code, test results and survey data. The analysis of that evidence must be in the body of the response, where it can earn marks.

See [](../06_documentation/18_appendices.md) for what counts towards the page and word limits.
:::

## Success Criteria

Develop success criteria by considering the problem from both the user's and the developer's perspective, and by breaking the problem down to identify what *quality*, *appropriate* and *secure* mean for this solution. Give each criterion a code (for example, SC1) so we can refer to it throughout the response.

Criteria should address:

- the user experience
- the technical outcomes
- security considerations for the data that are specific to the problem, such as confidentiality, integrity and availability

Evidence for: **Determining and Synthesising** (determining success criteria)

See [](../06_documentation/06_success_criteria.md).

## Possible Solutions

The three parts of the possible solution must work together as one system. Show how the user interface, the data and the back end relate to each other.

### User Interface

Show annotated mock-ups of the key screens. The annotations should:

- explain how the design applies the elements (space, line, colour, shape, texture, tone, form, proportion and scale) and principles (balance, contrast, proximity, harmony, alignment, repetition and hierarchy) of visual communication
- refer to the usability principles (accessibility, effectiveness, safety, utility and learnability) to justify design decisions
- show how the interface gives different users different levels of access, if the stimulus describes users with different roles
- show how graphs, logs and other visual representations display the data, where the stimulus calls for them
- show how the design meets the accessibility standards for the chosen technology (for example, a web or mobile application)
- show how the interface relates to the data and security design of the solution

Evidence for: **Determining and Synthesising** (user interfaces)

See [](../06_documentation/07_mock-ups.md), [](../03_user_experience/02_usability_principles.md) and [](../03_user_experience/03_visual_communication.md).

### Secure Data and Data Repositories

Use the secure data concepts that are relevant to our solution to justify our design decisions against the success criteria. We don't need to demonstrate every technique below, only those that suit the solution:

- data naming conventions, formats and structures
- secure data transmission techniques: encryption, decryption, authentication, hashing and checksums
- symmetric (DES, Triple DES, AES, Blowfish, Twofish) and asymmetric (RSA) encryption algorithms
- encryption and authentication strategies, such as two-factor and multi-factor authentication (verification codes compared with biometrics)
- the security principles of confidentiality, integrity and availability of data
- how the application's sub-systems (front end and back end) work together
- how data flows through the system, shown in data flow diagrams
- the Australian Privacy Principles, from a digital systems perspective

Evidence for: **Determining and Synthesising** (secure data and data repositories)

See [](../06_documentation/10_dfd.md), [](../06_documentation/11_erd_rs.md), [](../06_documentation/12_data_dictionaries.md), [](../06_documentation/13_data_exchange_diagrams.md), [](../05_data_transmission/02_privacy.md), [](../05_data_transmission/04_security_management.md) and [](../05_data_transmission/05_security_threats.md).

### Programmed Components

Show pseudocode that represents the solution's logic. Choose the constructs and features that are relevant to our solution, rather than trying to include everything below:

- the basic algorithm constructs: assignment, sequence, selection, condition, iteration and modularisation
- security-related algorithms
- the six basic features of programming: variables, control structures, data structures, syntax, libraries and classes
- good programming practice: dependability, efficiency, testing, debugging, error correction, coding conventions (commenting and naming conventions), code simplicity and portability
- receiving, processing and displaying data from an external source
- appropriate data formats for exchange, such as JSON or XML
- SQL statements where needed: CREATE, DROP, ALTER, INSERT, UPDATE, and SELECT with WHERE, GROUP BY, HAVING, ORDER BY, subqueries and inner joins

Evidence for: **Determining and Synthesising** (programmed components)

See [](../06_documentation/08_pseudocode.md), [](../02_coding/02_basic_features.md) and [](../02_coding/03_good_practice.md).

## Prototype Digital Solution

Show the prototype working, using annotated screenshots, annotated code snippets and a video of up to 2 minutes. The full code goes in the appendix. The prototype should show:

- working user interface screens for at least the core features
- programmed logic that demonstrates selection, iteration, user input and data output
- the components working together as one system: user actions changing the data, and data being retrieved and displayed securely

## Potential and Desired Impacts

Evaluate the impacts of the solution on **data security and privacy**, not the general impacts of the solution. Include:

- **personal impacts**, for example on the people whose data is collected or shared, and on the people who use the solution
- **social impacts**, for example on trust in the organisation and how the community sees its handling of data
- **economic impacts**, for example the cost of compliance, the cost and consequences of a data breach, and the resources needed

Make each judgment:

- specific to the problem and the solution we generated, not general commentary
- linked to the relevant Australian Privacy Principles and the risks to the confidentiality, integrity and availability of the data
- supported by evidence and specific, measurable outcomes rather than vague statements (a short list of key outcomes is acceptable)
- honest about constraints, for example where the prototype couldn't fully implement a security feature, and what that means for the impacts

See [](../06_documentation/17_impacts.md) and [](../05_data_transmission/02_privacy.md).

## Evaluation

Evaluate the prototype against the success criteria, covering:

- the **user experience**
- the **programmed components**, including their accuracy and maintainability
- the security considerations for the data

Each judgment should be specific and measurable, linked directly to a success criterion, and supported by evidence from testing or user feedback. The success criteria should guide what we test, so the evidence maps onto the criteria. A short list of key outcomes is acceptable instead of long paragraphs.

See [](../06_documentation/14_testing.md), [](../06_documentation/15_user_feedback.md) and [](../06_documentation/16_evaluation.md).

## Refinements and Recommendations

Include:

- the refinements we made to the solution during development
- recommendations for future improvements

Both must be explicitly justified by user feedback and testing outcomes, not general opinion.

See [](../06_documentation/16_evaluation.md).

:::{hint} Check your work: Evaluating
:class: dropdown
- Are the judgments explicitly connected to the success criteria?
- Is each judgment supported by specific evidence from testing or user feedback?
- Are the impacts on data security and privacy evaluated, not just described, and considered from different stakeholders' perspectives?
- Is there clear evidence of refinements made to the solution?
- Do the recommendations follow logically from the evaluation?
:::

Generating is worth 9 of the 25 marks. A working prototype that combines the user interface, data and programmed components is the most important part of IA3. Make sure it works reliably before spending time polishing the documentation.

## Communicating

Throughout the response:

- combine visuals with annotations and written or spoken features to describe, explain and justify decisions clearly, within the response limits
- use technical language accurately for a technical audience
- use accurate grammar and sentence structures
- reference all sources consistently using APA style

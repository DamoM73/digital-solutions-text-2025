# FIA1 - Technical Proposal

:::{dropdown} Learning Goals
By the end of this section you will:
- know the conditions and marks for the FIA1 technical proposal
- know how to structure your multimodal response
- know which documentation tools to use in each section, and which criteria they provide evidence for
:::

:::{tip} Assessment Details
- Technique: Investigation – technical proposal
- Unit: Unit 1 Creating with code
- Mode: multimodal, individual
- Length: up to 10 minutes, including annotations of up to 2000 words
- Marks:
  - Comprehending: 5
  - Analysing: 7
  - Synthesising: 6
  - Generating: 5
  - Communicating: 2
  - Total: 25
:::

In FIA1 we propose a digital solution to the problem described on the task sheet. We don't write any code. Instead, we investigate the problem, design a solution, and build a low-fidelity (non-coded) prototype that shows how the data and user interface work together. Our audience is technical, so we communicate like developers presenting to other developers.

:::{note} What is a multimodal presentation?
:class: dropdown
A multimodal presentation combines two or more modes of communication (for example, spoken narration, images, diagrams and written annotations) so that all of them work together to make meaning.

- Turning a written document into a slideshow or PDF **isn't** multimodal.
- The presentation doesn't need to be performed in front of the class. We can pre-record it and submit the video.
- Setting up before the recording starts (for example, adjusting the microphone) doesn't count towards the time limit.
:::

## Structuring your response

Use these headings in your presentation, and keep each section within its time limit.

| Heading | Time | Stage |
| --- | --- | --- |
| Introduction | up to 1 min | Introduce the problem and what we are proposing |
| The Analysis | up to 3 min | Explore |
| The Design | up to 3 min | Develop |
| The Proposed Solution | up to 2 min | Generate (non-coded prototype in action) |
| Conclusion | up to 1 min | Summarise how the proposal meets the success criteria |
| Bibliography | about 5 sec | Sources used |

:::{hint} Plan the time, not just the content
:class: dropdown
Ten minutes goes quickly. Explore and Develop each get only three minutes, so we can't talk through every row of every table. Show the diagram or table on screen, and use narration and annotations to highlight the important features and relationships.
:::

## The Analysis (Explore)

In the Explore section we analyse the problem before we design anything. Each tool below provides evidence for particular criteria, so include all of them.

### Mind map

Use the mind map to break down the problem. Make sure it covers:

- **scope**: what is included in the solution and what is excluded
- **constraints and limitations**
- **possible personal, social and economic impacts**
- the users, data, user interface and programmed components the problem involves

Evidence for: **Analysing** (features and relationships of programming and user interface), **Communicating**

:::{caution} Common mistake
:class: dropdown
A mind map that only lists topics is superficial. Draw cross-links between branches to show how ideas relate, such as how a constraint affects the user interface.
:::

See [](../06_documentation/02_mind_maps.md).

### Existing solutions

Analyse two or three existing solutions to similar problems using a Plus, Minus, Interesting table. Focus on the user interface and functionality, and finish by saying what we will adopt, improve or avoid in our own solution.

Evidence for: **Comprehending** (existing solutions), **Analysing**, **Communicating**

See [](../06_documentation/05_existing_solutions.md).

### Empathy maps and personas

Create an empathy map and a persona for each type of user named in the task. These show the problem from the user's perspective and help us find user-experience requirements.

Evidence for: **Analysing** (features and relationships of programming and user interface), **Communicating**

See [](../06_documentation/03_user_insight.md).

### Use case diagram

Show the actors (users and other systems) and the actions each can perform. Include the relationships between use cases, such as actions that require a login.

Evidence for: **Analysing** (features and relationships of programming and user interface), **Communicating**

See [](../06_documentation/04_use_case_diagrams.md).

### Requirements table

List the solution's requirements and prioritise them using a MuSCoW table. Make sure we have identified both:

- **programming requirements**, from the developer's perspective (what the solution must do and the data it needs)
- **user-experience requirements**, from the user's perspective (how users interact with the solution)

Evidence for: **Analysing** (programming requirements, user-experience requirements), **Communicating**

See [](../06_documentation/06_success_criteria.md).

### Criteria table

Write a success criterion for every **Must** and **Should** requirement. Each criterion needs to be specific, measurable and testable.

Evidence for: **Analysing** (success criteria), **Communicating**

:::{caution} Common mistake
:class: dropdown
"The website is easy to use" can't be tested. "Users can find and open any piece of work within three clicks from the home page" can.
:::

See [](../06_documentation/06_success_criteria.md).

## The Design (Develop)

In the Develop section we turn our analysis into possible solutions for the user interface and the algorithms.

### Mock-ups

Create annotated mock-ups of the key screens. The annotations are where most of the marks are, so explain *why* each design decision was made:

- name the **user-interface components** used, and why they suit the task
- explain how the design applies the **usability principles** and **visual communication principles**
- link design decisions to success criteria using codes (for example, SC3)

Evidence for: **Comprehending** (user-interface components, symbolisation of user interfaces, usability considerations), **Synthesising** (user interfaces), **Communicating**

See [](../06_documentation/07_mock-ups.md), [](../03_user_experience/02_usability_principles.md) and [](../03_user_experience/03_visual_communication.md).

### Pseudocode

Write pseudocode for the key algorithms in the solution. Choose the algorithms that do the most important processing, such as checking a user's login, enforcing rules like limiting each user to one action, or calculating and displaying results. Follow the QCAA pseudocode rules and annotate the pseudocode to explain how it meets the requirements.

Evidence for: **Synthesising** (algorithms), **Communicating**

See [](../06_documentation/08_pseudocode.md).

## The Proposed Solution (Generate)

Build a low-fidelity, non-coded prototype of the solution, then record it in action. The prototype needs to demonstrate the relationship between the **data** and the **user interfaces**. For example, show what the user sees before and after they submit something, and how the screens change as the data changes.

Evidence for: **Generating** (programmed components and user interfaces), **Communicating**

:::{hint} Show the flow, not just the screens
:class: dropdown
Walk through a realistic user journey from start to finish. Each step should show an action from the user, the data it changes, and the result on screen.
:::

See [](../09_tools/03_figma.md).

## Where the marks come from

This table shows which tools provide the evidence for each criterion.

| Criterion | Marks | Evidence in |
| --- | --- | --- |
| Comprehending: user-interface components | 5 (shared) | Mock-ups |
| Comprehending: existing solutions | | Existing solutions |
| Comprehending: symbolisation of user interfaces | | Mock-ups |
| Comprehending: usability considerations | | Mock-ups |
| Analysing: features and relationships of programming and user interface | 7 (shared) | Mind map, existing solutions, empathy maps, personas, use case diagram |
| Analysing: programming and user-experience requirements | | Requirements table |
| Analysing: success criteria | | Criteria table |
| Synthesising: user interfaces | 6 (shared) | Mock-ups |
| Synthesising: algorithms | | Pseudocode |
| Generating: programmed components and user interfaces | 5 | Non-coded prototype |
| Communicating: visual, spoken and written features, and technical language | 2 (shared) | All tools and the presentation itself |
| Communicating: grammatically accurate language | | Annotations and written text |
| Communicating: referencing conventions | | Bibliography |

:::{important} Mock-ups carry a lot of weight
Mock-ups provide evidence for three of the four Comprehending descriptors and half of Synthesising. Weak or missing mock-up annotations will cost marks across two criteria.
:::

## Communicating

- Use technical language accurately (for example, *user-interface component*, *validation*, *authentication*, *success criterion*).
- Check the spelling and grammar of every annotation and table. Written text is part of the presentation.
- Make sure the visuals are readable on screen. Zoom in on diagrams and tables while we talk about them.
- Reference all sources, including images and existing solutions, in the Bibliography.

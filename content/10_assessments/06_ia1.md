# IA1 - Technical Proposal

:::{dropdown} Learning Goals
By the end of this section you will:
- know the conditions and marks for the IA1 technical proposal
- know what the proposal must include, including the analysis of the datasets
- know which documentation tools to use in each section, and which criteria they provide evidence for
:::

:::{tip} Assessment Details
- Technique: Technical proposal
- Unit: Unit 3 Digital innovation
- Mode: multimodal, individual
- Length: up to 10 minutes, including annotations of up to 2000 words
- Duration: approximately 15 hours of class time. We can also work on it in our own time.
- Marks:
  - Comprehending: 5
  - Analysing: 7
  - Synthesising: 6
  - Generating: 5
  - Communicating: 2
  - Total: 25
:::

In IA1 we propose a digital solution to a real-world problem, then present the proposal to a technical audience. We don't write any code. Instead, we investigate the problem and the data, design a solution, and build a low-fidelity (non-coded) prototype that shows how the data and user interface work together.

IA1 builds on FIA1. The big difference is **data**. The stimulus includes datasets, and we need to analyse them, decide which data the solution will use, and design how that data will be stored. Data now appears in the Analysing, Synthesising and Generating criteria, and the Comprehending criterion asks us to explain how our data structures support the user experience.

:::{note} What is a multimodal presentation?
:class: dropdown
A multimodal presentation combines two or more modes of communication (for example, spoken narration, images, diagrams and written annotations) so that all of them work together to make meaning.

- Turning a written document into a slideshow or PDF **isn't** multimodal.
- The presentation can be pre-recorded and submitted as a video.
:::

## What the proposal must include

Make sure the proposal includes:

- a clear **problem statement** that identifies the client's needs
- a **user story** that defines the intended users and their needs
- an analysis of **existing solutions**, the **datasets** and the **constraints**
- a **data story** that explains how the selected data will be used to meet the client's needs
- **success criteria** that cover the personal, social and economic impacts of the solution, and its suitability and feasibility
- a **conceptual model** of the key components and structure of the solution, such as diagrams or annotated visuals
- a **low-fidelity, non-coded prototype** that shows the relationship between the data and the user interface
- accurate referencing of all sources, including the **data sources**

## Explore

In the Explore section we analyse the problem, the users and the data before we design anything.

### Mind map

Break down the problem. Cover the scope (what is included and excluded), constraints and limitations, possible personal, social and economic impacts, and the users, data, user interface and programmed components involved. Draw cross-links to show how the ideas relate.

Evidence for: **Analysing** (features and relationships of data, programming and user interface)

See [](../06_documentation/02_mind_maps.md).

### Existing solutions

Analyse existing solutions to similar problems. Connect what we find to our own solution: which features and interface components we will adopt, improve or avoid, and why. Comment on their usability.

Evidence for: **Comprehending** (existing solutions, usability considerations), **Analysing**

See [](../06_documentation/05_existing_solutions.md).

### Empathy maps and personas

Create an empathy map and a persona for each type of user. Use them to write the user story and to find user-experience requirements.

Evidence for: **Analysing** (features and relationships of data, programming and user interface)

See [](../06_documentation/03_user_insight.md).

### Use case diagram

Show the actors and the actions each can perform, including the relationships between use cases.

Evidence for: **Comprehending** (interrelationships between data and user experience), **Analysing**

See [](../06_documentation/04_use_case_diagrams.md).

### Data analysis

Analyse the current data and the alternative datasets provided in the stimulus. For each dataset, consider:

- what data it contains, and whether it meets the client's needs
- its quality: missing values, errors, duplicates and inconsistent formats
- its source, licence and how it must be referenced
- privacy and security concerns, especially for personal data

Then decide which data the solution will use, and explain how it will need to be cleaned, merged or organised. This becomes our **data story**.

Evidence for: **Analysing** (features and relationships of data)

See [](../04_data/01_intro.md), [](../04_data/02_data_principles.md), [](../07_python/03_csv.md) and [](../05_data_transmission/02_privacy.md).

### Data flow diagram

Show how data moves between the users, the processes in the solution and the data stores.

Evidence for: **Comprehending** (interrelationships between data and user experience), **Analysing**, **Synthesising** (data)

See [](../06_documentation/10_dfd.md).

### Requirements table

List the solution's requirements and prioritise them using a MuSCoW table. Identify both **programming requirements** (from the developer's perspective) and **user-experience requirements** (from the user's perspective), and the **data** the solution requires.

Evidence for: **Analysing** (programming requirements, user-experience requirements)

See [](../06_documentation/06_success_criteria.md).

### Criteria table

Write a success criterion for every **Must** and **Should** requirement. Include criteria for the personal, social and economic impacts, and for the suitability and feasibility of the solution. Each criterion needs to be specific, measurable and testable, and specific to this problem.

Evidence for: **Analysing** (success criteria)

See [](../06_documentation/06_success_criteria.md).

:::{hint} Check your work: Analysing
:class: dropdown
- Have we analysed the scope, constraints, limitations and possible impacts?
- Have we considered the relevance and quality of the data?
- Do the requirements and success criteria consider the user's perspective, the developer's perspective and the required data?
- Are the success criteria specific to this problem, rather than applicable to almost any digital solution?
:::

## Develop

In the Develop section we design the possible solutions for the user interface, the data and the algorithms.

### Mock-ups

Create annotated mock-ups of the key screens. Annotations should:

- name the user-interface components used, and why they suit the task
- explain how the design applies the usability principles, including navigation flow, accessibility, input and output, and layout
- explain how the data is entered, displayed and changed on each screen
- link design decisions to success criteria using codes (for example, SC3)

Evidence for: **Comprehending** (user-interface components, symbolisation of user interfaces, usability considerations), **Synthesising** (user interfaces)

See [](../06_documentation/07_mock-ups.md), [](../03_user_experience/02_usability_principles.md) and [](../03_user_experience/03_visual_communication.md).

### ERD and relational schema

Design the database structure for the data we selected. Normalise the data, then show the entities, their relationships, and the primary and foreign keys.

Evidence for: **Synthesising** (data)

See [](../06_documentation/11_erd_rs.md) and [](../04_data/03_structuring_data.md).

### Data dictionary

Describe every field in the database: its name, data type, size, constraints and a description.

Evidence for: **Synthesising** (data)

See [](../06_documentation/12_data_dictionaries.md).

### Pseudocode

Write pseudocode for the key algorithms, including how data is retrieved and changed. The pseudocode should be structured, unambiguous and specific to the programming requirements and success criteria.

Evidence for: **Synthesising** (algorithms)

See [](../06_documentation/08_pseudocode.md).

:::{hint} Check your work: Synthesising
:class: dropdown
- Do the mock-ups, data design and pseudocode work together as one system?
- Do the mock-ups consider the data and the algorithms, not just the layout?
- Does the pseudocode address specific programming requirements and success criteria?
- Is the data selected, cleaned, merged and organised based on the requirements?
:::

## Generate

Build a low-fidelity, non-coded prototype of the solution, then demonstrate it in the presentation. The prototype must show how interacting with the user interface **accesses**, **changes** and **displays** the data.

Evidence for: **Comprehending**, **Synthesising** (user interfaces), **Generating** (data and user interfaces)

:::{hint} Check your work: Generating
:class: dropdown
- Does the prototype clearly show how user actions access, change and display the data?
- Does the prototype meet the requirements and the success criteria?
- Does it show how our initial ideas were refined?
:::

See [](../09_tools/03_figma.md).

## Communicating

- Combine visuals with narration and annotations so each one explains and justifies a decision.
- Use technical language accurately for a technical audience.
- Check the spelling and grammar of every annotation and table.
- Reference all sources, including the datasets, images and existing solutions.
- Make sure the visuals are readable on screen, and stay within the time and word limits.

# IA2 - Digital Solution

:::{dropdown} Learning Goals
By the end of this section you will:
- know the conditions and marks for the IA2 digital solution
- know how to structure your response and what belongs in an appendix
- know which documentation tools to use in each phase, and which criteria they provide evidence for
:::

:::{tip} Assessment Details
- Technique: Digital solution
- Unit: Unit 3 Digital innovation
- Mode: multimodal, individual
- Length:
  - visual and written: up to 10 A4 pages, including annotations of up to 1500 words
  - visual and spoken: a video of up to 2 minutes
- Duration: approximately 15 hours of class time. We can also work on it in our own time.
- Marks:
  - Determining and Synthesising: 7
  - Generating: 9
  - Evaluating: 7
  - Communicating: 2
  - Total: 25
:::

In IA2 we build a working prototype of a database-driven application. The stimulus describes the client, their requirements and their users. Our job is to determine success criteria, design and code the solution, then test it, gather user feedback and evaluate it.

IA2 builds on FIA2 and FIA3. Like FIA2, we build the whole application, including the user interface. Like FIA3, the application stores its data in a database. This means every criterion now involves three kinds of component: the **user interface**, the **data and data repositories**, and the **programmed components**.

Our code must demonstrate **selection**, **iteration**, **user input** and **data output**.

## Structuring your response

Use headings that follow the phases of the problem-solving process.

| Phase | Sections |
| --- | --- |
| Explore | Criteria table |
| Develop | Mock-ups, data flow diagram, ERD and relational schema, data dictionary, pseudocode |
| Generate | Annotated code snippets, prototype video |
| Evaluate and Refine | Testing summary, user feedback, impacts assessment, product evaluation |
| Bibliography | APA references (excluded from the page count) |
| Appendix | Code, user feedback survey, testing results |

:::{important} What goes in the appendix
:class: dropdown
Markers can't use anything in the appendix when marking. The appendix is for raw evidence only: full code, survey data and test results. The analysis of that evidence (our summaries, evaluation, refinements and recommendations) must be in the body of the response, where it can earn marks.

See [](../06_documentation/18_appendices.md) for what counts towards the page and word limits.
:::

## Explore

### Criteria table

Use the stimulus to write success criteria. The stimulus provides the functional requirements, the non-functional requirements (such as usability and visual communication) and the user profiles. Give each criterion a code (for example, SC1) so we can refer to it throughout the response.

Strong success criteria:

- consider the user's perspective, the developer's perspective and the data required
- break the problem down (decomposition), look for patterns (pattern recognition) and focus on what matters (abstraction) to find specific measures of quality, appropriateness and effectiveness
- address both the **user experience** and the **technical outcomes**
- are specific, measurable and testable, so we can use them in testing and evaluation

Evidence for: **Determining and Synthesising** (determining success criteria)

See [](../06_documentation/06_success_criteria.md).

## Develop

In the Develop section we design the possible solutions for the user interface, the data and the programmed components. These designs need to work together as one system.

### Mock-ups

Design the key screens before we build them. Annotate the mock-ups to explain how each design decision applies the usability and visual communication principles, how the data is entered and displayed, and which success criteria it meets.

Evidence for: **Determining and Synthesising** (user interfaces)

See [](../06_documentation/07_mock-ups.md), [](../03_user_experience/02_usability_principles.md) and [](../03_user_experience/03_visual_communication.md).

### Data flow diagram

Show how data moves between the users, the processes in the solution and the data stores.

Evidence for: **Determining and Synthesising** (data and data repositories)

See [](../06_documentation/10_dfd.md).

### ERD and relational schema

Design the database. Normalise the data, then show the entities, their relationships, and the primary and foreign keys.

Evidence for: **Determining and Synthesising** (data and data repositories)

See [](../06_documentation/11_erd_rs.md) and [](../04_data/03_structuring_data.md).

### Data dictionary

Describe every field in the database: its name, data type, size, constraints and a description. Include the validation and constraints that protect the integrity of the data.

Evidence for: **Determining and Synthesising** (data and data repositories)

See [](../06_documentation/12_data_dictionaries.md).

### Pseudocode

Represent the key programmed components in pseudocode. The pseudocode should be structured, unambiguous and specific to this problem, and show how the components work together, for example how a user action triggers a query and updates the display.

Evidence for: **Determining and Synthesising** (programmed components)

See [](../06_documentation/08_pseudocode.md).

:::{hint} Check your work: Determining and Synthesising
:class: dropdown
- Do the success criteria consider the user's perspective, the developer's perspective and the required data?
- Is there evidence of decomposition, pattern recognition and abstraction in the success criteria?
- Are the success criteria authentic, addressing both user experience and technical outcomes?
- Do design thinking and systems thinking inform the mock-ups?
- Is the pseudocode structured, unambiguous, specific to the problem and aligned with the success criteria?
- Is the data organised and structured, including the data repositories, based on the solution and the success criteria?
:::

## Generate

### Annotated code snippets

Choose the code snippets that show the most important programmed components. Annotate each one to explain what it does, why we wrote it that way, and which success criterion it meets. The full code goes in the appendix.

Choose snippets that show:

- how the user interface, data and programmed components connect (for example, a button connected to a method that queries the database and updates the display)
- SQL queries that join, filter or summarise data, and statements that add, update or delete data
- how the solution protects the data, such as input validation and parameterised queries
- selection, iteration, user input and data output

Evidence for: **Generating**

See [](../07_python/02_pyqt.md), [](../07_python/05_sql_and_python.md), [](../07_python/06_queries.md), [](../07_python/06_update_delete.md), [](../07_python/08_populate.md) and [](../02_coding/03_good_practice.md).

### Prototype video

Record a video of up to 2 minutes demonstrating the prototype working. Show every feature in action, including how the user interface responds to user input and how the data in the database changes.

Evidence for: **Generating**, **Communicating**

:::{hint} Check your work: Generating
:class: dropdown
- Are the user interface, data and programmed components fully combined into one working system?
- Does the prototype behave consistently and reliably every time?
- Does the solution meet the requirements, user needs and success criteria?
:::

## Evaluate and Refine

### Testing summary

Test the programmed components (unit testing) and how they work together (integrated testing). Put the testing results in the appendix, and summarise the key results in the body, referring to specific test cases.

See [](../06_documentation/14_testing.md).

### User feedback

Survey users about the prototype. Align the survey questions with the success criteria and the usability principles. Put the raw survey data in the appendix, and summarise the key findings in the body.

See [](../06_documentation/15_user_feedback.md).

### Impacts assessment

Identify the potential and desired impacts of the solution, then evaluate its personal, social and economic impacts within the context of the problem. Consider positive and negative impacts from the perspectives of different stakeholders, and support each judgment with reasoning.

See [](../06_documentation/17_impacts.md).

### Product evaluation

Evaluate the solution against each success criterion. Each judgment must be supported by specific evidence from testing or user feedback, and must cover both the **user experience** and the **programmed components**, including their accuracy and maintainability. Include the refinements we made during development and recommendations for the future, each justified by testing or user feedback.

See [](../06_documentation/16_evaluation.md).

Evidence for all of the above: **Evaluating**, **Communicating**

:::{hint} Check your work: Evaluating
:class: dropdown
- Are the judgments explicitly connected to the success criteria?
- Is each judgment supported by specific evidence from testing or user feedback?
- Are impacts evaluated, not just described, and considered from different stakeholders' perspectives?
- Is there clear evidence of refinements made to the solution?
- Do the recommendations follow logically from the evaluation?
:::

## Where the marks come from

| Criterion | Marks | Evidence in |
| --- | --- | --- |
| Determining and Synthesising: success criteria | 7 (shared) | Criteria table |
| Determining and Synthesising: user interfaces | | Mock-ups |
| Determining and Synthesising: data and data repositories | | Data flow diagram, ERD and relational schema, data dictionary |
| Determining and Synthesising: programmed components | | Pseudocode |
| Generating: prototype combining user-interface, data and programmed components | 9 | Annotated code snippets, prototype video |
| Evaluating: user experience and programmed components against criteria | 7 (shared) | Product evaluation, testing summary, user feedback |
| Evaluating: impacts | | Impacts assessment |
| Evaluating: refinements and recommendations | | Product evaluation |
| Communicating | 2 | The whole response |

:::{important} Generating is the biggest criterion
Generating is worth 9 of the 25 marks. A working prototype that combines the user interface, data and programmed components is the most important part of IA2. Make sure it works reliably before spending time polishing the documentation.
:::

## Communicating

- Combine visuals with annotations so each one explains and justifies a decision.
- Use technical language accurately for a technical audience.
- Check the spelling and grammar of every annotation and table.
- Reference all sources using APA style, including in-text citations.
- Stay within the page, word and video limits.

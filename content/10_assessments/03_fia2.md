# FIA2 - Digital Solution

:::{dropdown} Learning Goals
By the end of this section you will:
- know the conditions and marks for the FIA2 digital solution
- know how to structure your response and what belongs in an appendix
- know which documentation tools to use in each phase, and which criteria they provide evidence for
:::

:::{tip} Assessment Details
- Technique: Project – digital solution
- Unit: Unit 1 Creating with code
- Mode: multimodal, individual
- Length:
  - visual and written: up to 10 A4 pages, including annotations of up to 1500 words
  - visual and spoken: a video of up to 2 minutes demonstrating the user interface, data and programmed components
- Marks:
  - Determining and Synthesising: 7
  - Generating: 9
  - Evaluating: 7
  - Communicating: 2
  - Total: 25
:::

In FIA2 we build a working prototype of a digital solution. The stimulus is a technical proposal, so much of the analysis is already done for us: the requirements, personas and constraints are in the stimulus. Our job is to determine success criteria from that proposal, design and code the solution, then test it, gather user feedback and evaluate it.

Our code must demonstrate **selection**, **iteration**, **user input** and **data output**.

## Structuring your response

Use headings that follow the phases of the problem-solving process.

| Phase | Sections |
| --- | --- |
| Determine and Synthesise | Success criteria, wireframes, pseudocode |
| Generate | Annotated code snippets, prototype video |
| Evaluate | User feedback summary, testing summary, evaluation table, impacts table, recommendations table |
| Bibliography | APA references (excluded from the page count) |
| Appendix | Code, testing tables, user feedback survey data |

:::{important} What goes in the appendix
:class: dropdown
Markers can't use anything in the appendix when marking. The appendix is for raw evidence only: full code, test results and survey data. The analysis of that evidence (our summaries, evaluation and recommendations) must be in the body of the response, where it can earn marks.

See [](../06_documentation/18_appendices.md) for what counts towards the page and word limits.
:::

## Determine and Synthesise

### Success criteria

Read the stimulus carefully and use its requirements, personas and constraints to write success criteria. Give each criterion a code (for example, SC1) so we can refer to it throughout the response.

Strong success criteria:

- address both the **user experience** and the **technical outcomes**
- consider the problem from both the user's perspective and the developer's perspective
- are tailored to this problem, not generic
- are specific, measurable and testable, so we can use them in testing and evaluation

Evidence for: **Determining and Synthesising** (determining success criteria)

See [](../06_documentation/06_success_criteria.md).

### Wireframes

Design the user interface before we build it. Annotate the wireframes to explain how each design decision applies the usability and visual communication principles, and link decisions to success criteria using their codes.

Evidence for: **Determining and Synthesising** (possible solutions for user interfaces)

See [](../06_documentation/07_mock-ups.md), [](../03_user_experience/02_usability_principles.md) and [](../03_user_experience/03_visual_communication.md).

### Pseudocode

Write pseudocode for the key algorithms. The pseudocode should be specific to this problem and show how the components work together, for example how a button press changes the data and then updates the display.

Evidence for: **Determining and Synthesising** (possible solutions for programmed components)

See [](../06_documentation/08_pseudocode.md).

:::{hint} Check your work: Determining and Synthesising
:class: dropdown
- Do the success criteria consider both the user's and the developer's perspectives?
- Are the success criteria authentic, addressing both user experience and technical outcomes?
- Does design thinking inform the wireframes?
- Is the pseudocode structured, unambiguous and specific to the problem?
- Do the components work together as a system, and does the design align with the success criteria?
:::

## Generate

### Annotated code snippets

We can't fit all our code in the response, so choose the snippets that show the most important programmed components. Annotate each one to explain what it does, why we wrote it that way, and which success criterion it meets. The full code goes in the appendix.

Choose snippets that show:

- how the user interface and programmed components connect (for example, a button connected to the method that updates the data and the display)
- selection, iteration, user input and data output
- how data is saved to and loaded from a file, if the solution does this

Evidence for: **Generating**

See [](../07_python/02_pyqt.md), [](../02_coding/03_good_practice.md), [](../07_python/03_csv.md) and [](../07_python/09_json.md).

### Prototype video

Record a video of up to 2 minutes demonstrating the prototype working. Show every feature in action, including how the user interface responds to user input and how the data changes.

- Save it in mp4 format.
- Keep it to 200 MB or less.
- Plan the demonstration before recording so it fits within 2 minutes.

Evidence for: **Generating**, **Communicating**

:::{hint} Check your work: Generating
:class: dropdown
- Are the user interface and programmed components fully combined into one working system?
- Does the prototype behave consistently and reliably every time?
- Does the solution meet the requirements, user needs and success criteria?
:::

## Evaluate

### User feedback summary

Survey users about the prototype. Align the survey questions with the success criteria and the usability principles. Put the raw survey data in the appendix, and summarise the key findings in the body.

See [](../06_documentation/15_user_feedback.md).

### Testing summary

Test the programmed components (unit testing) and how they work together (integrated testing). Put the testing tables in the appendix, and summarise the key results in the body, referring to specific test cases.

See [](../06_documentation/14_testing.md).

### Evaluation table

Evaluate the solution against each success criterion. Each judgment must be supported by specific evidence from testing or user feedback, and must cover both the **user experience** and the **programmed components**, including their accuracy and maintainability.

See [](../06_documentation/16_evaluation.md).

### Impacts table

Evaluate the personal, social and economic impacts of our solution within the context of the problem. Consider positive and negative impacts from the perspectives of different stakeholders, and support each judgment with reasoning.

See [](../06_documentation/17_impacts.md).

### Recommendations table

List the refinements we made during development and recommendations for future versions. Each one must be justified by evidence from testing or user feedback.

Evidence for all of the above: **Evaluating**, **Communicating**

:::{hint} Check your work: Evaluating
:class: dropdown
- Are the judgments explicitly connected to the success criteria?
- Is each judgment supported by specific evidence from testing or user feedback?
- Are impacts evaluated, not just described, and connected to the solution and the problem?
- Is there clear evidence of refinements made to the solution?
- Do the recommendations follow logically from the evaluation?
:::

## Where the marks come from

| Criterion | Marks | Evidence in |
| --- | --- | --- |
| Determining and Synthesising: success criteria | 7 (shared) | Success criteria |
| Determining and Synthesising: user interfaces | | Wireframes |
| Determining and Synthesising: programmed components | | Pseudocode |
| Generating: prototype combining user-interface and programmed components | 9 | Annotated code snippets, prototype video |
| Evaluating: features and components against criteria | 7 (shared) | Evaluation table, testing summary, user feedback summary |
| Evaluating: impacts | | Impacts table |
| Evaluating: refinements and recommendations | | Recommendations table, evaluation table |
| Communicating | 2 | The whole response |

:::{important} Generating is the biggest criterion
Generating is worth 9 of the 25 marks. A working prototype that meets the requirements is the most important part of FIA2, so make sure it works reliably before spending time polishing the documentation.
:::

## Communicating

- Combine visuals with annotations so each one explains and justifies a decision.
- Use technical language accurately for a technical audience.
- Check the spelling and grammar of every annotation and table.
- Reference all sources using APA style, including in-text citations.
- Stay within the page, word and video limits.
